## 1. 我理解的你要什么

（逐条可纠正；这一节是整份方案的判据）

1. **不是做平台，是做团队的那一层语义**。载体是 DSH 插件行；不建服务器、不建控制台、不上数据库、不自己路由模型。
2. **人的界面是飞书群**，用群里的话办事（中文动词，不用斜杠命令）；面板是**看板**，不是第二个产品。
3. **真相在工作区文件里**：契约、验收标准、台账、决策、记忆都是文件，git 管历史。飞书、面板、DSH 会话都只是**视图**。
4. **干活的是 DSH 会话**：群里那台机器人是**编排者**（需求分析师 / Tech Lead），重活按层扇出给子代理并行做，集成收口，结论回群。
5. **流程只有两道硬门禁**：① 契约 + 基线冻结（需求人签字）；② 合并（**只允许真人**）。冻结之后改需求必须走变更单。
6. **人是评审与验收**：AI 预审 ≠ 通过；实现者不该给自己签字（兼任阶段靠"先冻结再开工 + AI 对抗预审 + 合并必须真人"来补）。
7. **上下文要省**：一群一会话；跨群、跨层共享的是**文件**，不是上下文；每轮固定进上下文的东西越少越好。
8. **可追溯**：每一次状态变化都有**谁、什么时候、凭什么**（文件签字 + git 提交 + 事件行）；查不到就是没做。

## 2. 五条第一原则

1. **文件是真相，插件是唯一写路径。** 真相 = `tasks/*.md` 的机器字段 + `contracts/`；索引 `TASKS.md` 是**生成物**（声明为派生，手改会被覆盖）；插件用原子写 + 校验，人手改坏了就**拒绝写入并指出哪一行**。
2. **依赖只向内。** `app → surfaces → adapters → ports → kernel`；`kernel/` 里**不许出现任何 IO**（不读文件、不发请求、不看时钟）。这条能用测试扫源码强制。
3. **一个概念一处定义。** 身份、@ 剥离、状态名、台账字段、动词表、判据词表各只有一份；出现第二份就是 bug。
4. **每个动作要么留下文件变更，要么留下事件行，绝不静默。** 拒绝也要说清为什么（"记录是地板"）。
5. **门禁只有两道，且必须是真人。** 结构性保证：合并这条路径上**不存在**以机器人为主体执行的代码分支。

## 3. 分层与模块预算

```
plugin/
├── index.js           入口（≤120 行）：boot-safe，只做挂载
├── app/               组合根：config、装配、生命周期
├── kernel/            纯语义，零 IO —— 全部可单测，不需要 fake
│   ├── records.js         需求/任务记录的字段与不变量
│   ├── ledger.js          状态机 + 派生状态 + 一致性校验（不碰文件）
│   ├── gates.js           两道签字与"谁能签"
│   ├── render.js          记录 → markdown（frontmatter + 表格行）
│   └── parse.js           markdown → 记录（严格，报行号）
├── ports/             接口（没有实现）：ledger 文件、事件流、通信面、会话、时钟、日志
├── adapters/          实现
│   ├── fs-ledger.js       读写 tasks/*.md + 生成 TASKS.md + git 提交
│   ├── events.js          追加写事件流（JSONL），按月轮转
│   ├── feishu.js          一条长连接：收消息、发消息、更新一张卡
│   └── dsh.js             会话：创建/复用、驱动一轮、拿回复
├── surfaces/
│   ├── verbs.js           群里的话 → 动作（动词表只有这一份）
│   ├── cards.js           一张需求卡（原地更新）+ 纯文本兜底（只有两级）
│   ├── tools/             ledger / req / task / repo / docs（5 个工具）
│   └── panel/             台账 / 群 / 文档 / 日志（4 个视图，各一个模块）
└── panel-index.js     浏览器半边入口
```

**预算与约束**（写进测试，超了就红）：

| 约束 | 值 |
|---|---|
| 单文件行数 | ≤ 400（入口 ≤ 120） |
| `kernel/` 里出现 `fs`/`fetch`/`Date.now` | 直接失败 |
| 总行数 | ≤ 6,000（含 surfaces/panel） |
| 每个配置键 | 必须被 `lib` 里某处读过，否则配置检查报错 |
| 每个动词 | 必须有群里的说法 + 一个 handler，两边逐条对账 |

## 4. 工作区与台账文件规范

```
<workspace>/                     ← 项目根（不是 git 仓，只是容器：一个会话横跨所有仓）
├── AGENTS.md                    路由表：哪个仓归哪层、git 怎么跑（人写，AI 每轮读）
├── TASKS.md                     **生成物**：活跃项索引（需求表 + 任务表）
├── tasks/R-001.md               需求详情
├── tasks/T-001-2.md             任务详情
├── contracts/R-001.yaml|sql|md  跨层契约（冻结后只读，改动走变更单）
├── archive/2026-09/R-001.md     验收/废弃后按月归档（移动文件，不改内容）
├── docs/                        团队文档层（frontmatter 硬要求、索引可重建、陈旧报告）
└── <repo>/                      各代码仓（git clone / worktree）
```

**需求详情**（机器字段在 frontmatter，正文归人/AI；插件**只改 frontmatter**，正文一个字节都不动）：

```markdown
---
id: R-001
title: 订单导出支持按门店筛选
state: frozen                 # draft|frozen|building|review|accepted|changed|blocked|dropped
requester: human:wangmengfan  # 提需求的人（唯一）
acceptor: human:wangmengfan   # 验收人（与实现者分开的字段，第一天就分开填）
layers: [service, data]
repos: [main-repo]
priority: P1
frozen_by: { by: human:wangmengfan, at: 2026-09-12T15:00:00Z, what: "契约 v1 + 验收标准" }
merged_by: null
accepted_by: null
changes: []                   # 变更单：{id, at, by, what, impact, confirmed_by}
---
## 目标
## 验收标准
- [ ] 按门店筛选返回 ≤ 50 条，分页不变
## 背景与讨论
```

**任务详情**：`id / req / layer / repo / branch / assignee / state / evidence[] / reviewer / review_note / run`。
`layer ∈ {contract, frontend, service, data, integration, docs}`。

**写路径（三条，只有这三条）**：

1. **会话工具**（首选）：`task submit …` → 插件校验 → 原子写 → `git commit`（消息带 `Req:` / `Task:` trailer 与 actor）。
2. **群动词**：`确认 R-001` / `验收 R-001` → 同一条写路径（动词与工具共用 handler）。
3. **人手改文件**：允许（文件就是给人改的）。插件每次读都重新解析，不做"缓存即真相"；解析失败就在群里与面板说清**哪一行**，并**拒绝一切写入**直到修好；外部改动记一条事件行。

**索引是派生**：`TASKS.md` 每次写入后整份重建（活跃项 ≤ 200 行）。人若手改它，下次写入即被覆盖 —— 这是声明过的行为，不叫丢数据。

## 5. 状态与门禁（最小模型）

**需求 6 态**（`changed`/`blocked`/`dropped` 是旁路）：

```
draft ──冻结(门禁1:需求人签字)──► frozen ──有任务在跑──► building ──全部任务 done + 集成报告──► review ──验收签字──► accepted
  ▲                                  │                                                                      │
  └──────────── changed ◄──变更单─────┘                                                    blocked / dropped ─┘
```

**任务 5 态**：`todo → doing → review → done`（旁路 `blocked` / `dropped`）。

| 跃迁 | 硬要求（不满足就拒绝，并说清缺什么） |
|---|---|
| `draft → frozen` | 需求人本人签字；验收标准非空；跨层需求必须有 `contracts/` 文件 |
| 层任务 `todo → doing` | 契约任务已 `done`；有 `branch`；`assignee` 在册 |
| `doing → review` | 至少一条证据（commit sha / 文件路径 / 测试输出），空证据不算 |
| `review → done` | **真人**评审签字（AI 只能提案，不能自己收工） |
| 需求 `review → accepted` | 验收人签字；`accepted_by` 与最后实现者**记录上分开**（同一人时写 `self_review: true` 并在面板标出来 —— 不假装分开） |
| 合并（`repo merge`） | **actor 必须是真人**（bots 走这条路直接被拒，代码里没有机器分支）；CI 通过；至少一名真人评审 |

**没有的东西**（旧版有，V2 砍掉，理由见 §13）：门禁快照、跨域并行确认、代确认人、超时自动释放、租约 4 态、四道门禁、升级链。

**运行锁**（替代租约）：一个任务同一时刻只有一个 run。`run: {by, started_at, heartbeat}`；心跳超时 → 任务 `blocked` + 群里说一句"它卡在哪一步"。**不需要 4 个状态的租约机**：要的只是"别跑两遍"和"卡住能被看见"。

## 6. 群与会话

| 群 | persona | 会话 | 职责 |
|---|---|---|---|
| `#项目-需求` | 需求分析师 | 一条独立 DSH 会话 | intake、契约确认、变更单、验收 |
| `#项目-开发` | Tech Lead | 一条独立 DSH 会话 | 拆解、派发、扇出、集成收口、评审门禁 |
| `#项目-审核`（可选） | 预审员 | 一条 | 交叉评审报告（先不建） |
| 单聊 | 个人助手 | 一条 | 私人查询，不进台账 |

- **一个飞书应用可以服务多个群**（一样一张脸、一个人格配置文件不同）。只在"这个群需要一个**不同的群成员身份**"时才加第二个应用 —— 今天那两个应用正好对应两个群。
- **persona 是配置，不是飞书身份**：`chats: { <chatId>: { persona: tech-lead } }`，人格文件放工作区 `.dsh/personas/`，由 DSH 的技能机制加载。
- **这样做直接删掉一整类 bug**：今天折腾最久的"哪个机器人收到了、谁回答了、会话算谁的、open_id 属于哪个应用"——在"一群一台机器人"下不存在。

**入站三条路**（一条消息只会走其中一条，判定写在日志里）：

1. **动词**（`确认 R-001` / `跑 T-001-2`）：直接走状态机，**不排在模型后面等**。
2. **工作**（开发群里指到某个任务/需求的话）：进该群会话，作为工作指令。
3. **闲聊/提问**：只回答，**不建任何对象**（这一点是 2026-09-12 的明确要求：先放开那道控制）。

**出站**：一次状态变化 → **一条短消息**（`R-001 已冻结 · 契约 v1 · tasks/R-001.md`）；每个需求**一张卡原地更新**（只有这一种卡）；卡片渲染坏了降到纯文本（**两级**，不是五级）。@人配额、发言占比告警、节流 digest 这些**管制**机制砍掉，只保留**度量**（面板上一个数：机器人发言占比）。

## 7. 执行

- **编排者在群里，干活在子代理里**：`跑 T-001-2` → 插件把工作指令交给该群会话（带任务文件、AGENTS.md 路由、红线）→ 会话按层/按需**扇出子代理**（契约 / 前端 / 服务 / 数据 / 集成）→ 只把结论与证据回群。
- **插件不实现调度器**：不做队列、不做优先级、不做抢占。并发由 DSH 会话与子代理机制承担，插件只保证"同一任务不跑两遍"（运行锁）与"跑完必须有回执"。
- **证据自动回写**：一轮结束 → 插件把 `session:<id>`（+ 会话产出的 commit / 文件 / 测试输出）写进任务 `evidence[]`，然后才允许 `submit`。
- **超时不是静默失败**：轮次超时（`exec.turnTimeoutMs`）→ 回群里说"我在等什么"，任务转 `blocked`。
- **上下文纪律**：每轮进上下文的固定四样（系统提示 + 工具 + AGENTS.md + TASKS.md 索引）；详情按需读 `tasks/*.md`；**跨群共享文件，不共享上下文**。

## 8. 观测与可追溯

| 载体 | 内容 | 谁写 |
|---|---|---|
| **git** | 台账/契约/文档的每一次变更，`Req:`/`Task:` trailer + actor | 插件（唯一写路径） |
| **事件流** `~/.dsh/team/events/*.jsonl` | 每条入站消息的结论与原因、每次跃迁、每次拒绝、每次投递、每次外部改动 | 插件，**只追加**，按月轮转 |
| **群 transcript** `~/.dsh/team/groups/<chatId>/*.jsonl` | 群里说了什么、谁说的、机器人回了什么 | 插件，只追加 |

## 10. 失败与降级

1. **boot-safe**：入口只记日志、绝不 throw；另挂一条不依赖实现的自述路由（今天这条已跑通，照搬）。
2. **逐条降级并如实说**：缺会话能力 → `跑 T-001-2` 明确回"现在没有可用的执行会话"，其余照常。
3. **坏文件不猜**：解析失败 → 报行号 + 拒绝写入，不"尽力而为地理解"。
4. **发不出去也有记录**：出站失败进事件流并在面板标记，不重试到天荒地老。
5. **绝不静默**：任何被忽略的消息都要有一条带原因的记录（漏单可查）。

---

## 11. 不变量（用测试强制）

1. `kernel/` 里没有 IO（扫源码：`fs` / `fetch` / `Date.now` / `process`）。
2. 真相只在工作区文件里；`TASKS.md` 是生成物（删掉可重建）。
3. 写路径唯一：所有状态变化都过 `ledger` 校验 + git 提交。
4. 非法跃迁被拒，且拒绝消息说清**缺什么**。
5. 合并这条路径上不存在机器人主体（结构性检查，不是运行时判断）。
6. 未登记的人只能读；未登记的群不处理。
7. 同一任务不会并发跑两轮（运行锁）。
8. `done` 必须有证据；`accepted` 必须有验收人签字。
9. 每个动词在群里都有说法，且两边逐条对账（表驱动测试）。
10. 每个配置键都有消费者（否则配置检查报错）。
11. 单文件 ≤400 行、总行数 ≤6,000。
12. 手改坏的台账 → 报行号 + 拒绝写入（用例：改坏一个字段，写入被拒且文件未被截断）。

## 12. 实施分期

## 13. 明确不做（砍掉的旧设计 + 为什么）

| 砍掉 | 理由 | 什么条件下再做 |
|---|---|---|
| 插件自己的 JSON 对象台账 | 与"文件是真相"冲突，是漂移之源 | 不做了 |
| 任务 13 态 + 4 道门禁 + 门禁快照 | 为 10 人规模设计的协调机；你们 2–3 人 + AI 干活，付不起这个复杂度 | 真人 > 8 人、跨域确认真的成为瓶颈时 |
| 租约 4 态 + 三种释放 + 到期播报 | 要的只是"别跑两遍"+"卡住可见" | 出现多人抢同一任务时 |
| 决策对象 / 记忆 6 态 / 冲突收件箱 | ADR=文件、记忆=docs/、冲突=git | 出现自动化多写者时 |
| 卡片五级降级 + 5 种卡 + 按钮 | 按钮做不了（无公网回调），卡只需要"一张需求卡原地更新" | 有公网回调入口时 |
| @人配额 / 节流 digest / 发言占比告警 | 管制机制带来的复杂度 > 收益；保留**度量**即可 | 机器人真的开始刷屏时 |
| 名册 `bots[]` + 默认应用继承 + bridge 模式 | 一个群一台机器人已足够；多应用带来的身份歧义正是今天最痛的一类 bug | 某个群确实需要第二个群成员身份时 |
| 配置台（编辑/校验/备份/审计/预览/导入导出） | 配置就是文件；面板只显示"这个键有没有消费者" | 需要非工程同学改配置时 |
| 39 action 的超级工具 | 按对象拆 5 个工具，动词总数 ≈20 | 不做了 |
| 索引器 / 向量检索 / 云文档镜像 / 跨机同步 | 与"文件在 git 里"重复 | 文档量级上一个数量级后 |

## 14. 还没定（等你一句话，或我来定）

1. **审核群**要不要现在就建（交叉评审报告落哪里）—— 我倾向：先并入开发群，`评审 R-001` 的结论写进需求文件，等有独立评审人再拆群。
2. **按模块分群**（"多名 AI 工程师各负责不同业务模块"）—— 我倾向：**不按模块分群**，按层扇出子代理 + 每个模块一份 persona/技能文件；因为会话 cwd 不可变、子代理继承 cwd，分群会立刻撞上"跨仓协作"的墙（v3 §3.2 已论证）。
3. **面板是否保留写操作**（确认/验收/派发能不能在面板点）—— 我倾向：保留，但走**与群动词同一条写路径**（同一 handler），面板只是另一个入口。
