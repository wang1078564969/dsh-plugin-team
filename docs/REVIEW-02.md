## 1. 一句话结论

**这一轮抓到的两件事，都是"上一轮修了一半"和"承诺与实际不符"**：

1. **P0 修了一半**：`degradationLadder` 学会了尊重 `buttons:false`，但**真实调用点没传这个参数** ——
   第一天在群里建单看到的需求卡，仍然是一排点了没反应的死按钮，而且连文本替代指令都没有。
2. **`feishu.buttons: true` 是个假承诺**：插件从不注册 `card.action.trigger`，
   打开它只会得到死按钮，而且卡片不再给文本指令。

其余 20 条里，一半是"卡上写着能做、群里做不了"这类**跨模块漂移**（词表 ↔ handler ↔ 卡片按钮），
另一半是"静默降级没人知道"（缺 timer、身份探测失败、自检超时、配置被 row 固定）。

**这一轮最值得记住的一条**：第一轮修的那个 P0，之所以"看起来修好了"，是因为**测试只测了函数本身**——
`test/commands.test.mjs` 的对账测试也只造了 `in_progress` 一个状态。真正的教训是
"**修完要沿着真实调用点再走一遍**"，而不是"函数单测绿了就算完"。

## 3. 复核后下调 / 证伪的（别重复排查）

| 审查提出 | 复核结论 |
|---|---|
| "统一出口的 `bot:team` 兜底对工具调用不可达，闸用的是 `human:owner`" | ⚠️ **证伪**：实测无名册时不限制、有名册时闸用的确实是 `bot:team`（`create_requirement` 在名册非空时通过）。**但**这条指向了一个真问题：缺省负责人 `human:owner` 不在名册里时会被静默写进对象 —— 已按 R2-18 修 |

| "`degradationLadder` 的 `buttons:false` 让第 1、2 级内容完全相同、第 3 级永不出现" | ✅ 成立但**无害**：`uuid` 按 `via` 区分，幂等键不会重复；只是多了一级冗余。记在这里供以后精简 |
| "`test/commands.test.mjs` 不存在"（第一轮审查时） | ⚠️ 已补（本轮），并且**它当时确实漏了 `in_review` 状态** —— 这条批评是对的 |

## 4. 仍然没修、以及为什么不修

| 项 | 为什么留着 |
|---|---|
| **卡片按钮真的能用**（注册 `card.action.trigger` + 公网 HTTPS 回调） | 物理限制：DSH Web 只听 `127.0.0.1`。现在的处理是"拒绝打开这个开关 + 卡片给文本指令"，这是当前形态下的正解 |
| **卡片台账的保留窗口**（长期运行的安装会全量扫 `store.all('card')`，且降级率是全历史累计） | 需要先定窗口语义（观测口径会跟着变）。已记进 `docs/DESIGN.md` 的缺口表 |
| **审批三档**（允许一次 / 本次会话 / 始终） | 要接 DSH 的 approval 服务，属于新功能而不是补漏 |
| **语音 / 转发合并 / 撤回 / 表情四类入站** | 同上：是能力扩展，不是闭环缺口（当前四类都会"落库但不建单"，不漏） |
| **`assets/` 与 `store` 目录的清理策略** | 资产是消息内容（不是过程数据），清理需要产品决策；配置备份已经加了上限 |
| **面板给"提交验收"加证据输入框** | 现在的做法（如实说明没有证据）不会误导人；输入框是体验改进 |
