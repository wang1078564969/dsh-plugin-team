# 使用说明书

> 面向**用这套东西的人**：团队里配它的人、在群里用它的人、以及偶尔要排查"它怎么不动了"的人。
> 想知道内部怎么实现，读 `docs/DESIGN.md`；想读设计取舍，读 `../team-agent-architecture/`；
> 想看它现在缺什么，读 `docs/REVIEW-01.md` / `docs/REVIEW-02.md` / `docs/GAP-VS-DESIGN.md`。
>
> 本文写的每一个默认值、每一条命令，都在当前代码里核对过（2026-09-12，`518` 个用例全绿）。

## 1. 一分钟理解

```
群里说一句话 → 变成「需求」对象 → 拆成「任务」 → 两道人工确认 → 交给一个真实的 DSH 会话跑一轮
                                                                        ↓
                                                    汇报回写成证据 → 提交验收 → 群里播报 → 台账/面板可见
```

三件事决定了它和"客服机器人"不一样：

| | 说明 |
|---|---|
| **一个机器人 = 一个飞书应用 = 一个身份** | 多个机器人就是多个应用、多条长连接、多张脸。每个群有一个**主机器人**，群里所有消息都记在它名下 |
| **一个机器人 × 一个群 = 一份会话记忆** | 同一个人在 A 群和 B 群说的话不会串味；两个机器人在同一个群也不会共用一段记忆 |
| **它自己拨号，不要公网入口** | 长连接是插件自己连出去的。代价：**飞书里的卡片按钮点不动**（见 §13），确认动作走群文本命令 |

它落在**主机 DSH** 里：一个插件行、一个数据目录、一块面板（侧栏「团队台账」）。没有外部服务、没有数据库。

## 2. 装与开（第一次，5 分钟）

```console
# 1) 装进 profile（装包即装插件）
dsh plugin --profile web add link:/path/to/dsh-plugin-team

# 2) 起 web profile（面板只在 web profile 里有位置）
dsh --profile web

# 3) 用启动日志里那个带 ?token= 的地址打开 GUI
#    http://127.0.0.1:3080/?token=…      ← 少了 token 只会得到 401
```

打开后侧栏应当出现「**团队台账**」。点它 → 六个页签（台账 / 配置 / 机器人 / 成员 / 会话 / 日志）。

**装完必查两条**（少一条都可能"看起来装上了其实没生效"）：

```console
dsh --profile web --dump-config > /tmp/tree.yml
node ~/.dsh/profiles/web/plugins/inventory-check.cjs /tmp/tree.yml
#   entries checked: 153 → identified: 153, loose modules: 0, THROWING: 0
```

### 看不到侧栏入口？按顺序查这三件事

1. **起的是不是 web profile？** 面板要 `slots`，headless 里没有。
2. **地址里有没有 `?token=`？** GUI 的浏览器 cookie 是它换来的。
3. **插件加载失败了吗？** 插件是 **boot-safe** 的：它加载失败时**不会**拖垮 harness，
   代价就是"悄无声息"——入口不会出现、工具不会注册。失败原因一定写在这两个地方：

   ```console
   tail -5 ~/.dsh/team/load-report.txt     # 一行一次失败（load / activate）
   grep boot ~/.dsh/team/logs/team.jsonl   # 同一条错误的日志形态（插件起来后日志页也能看到）
   ```

## 3. 第一次配置

### 3.1 三样东西，按这个顺序配

| 顺序 | 在哪配 | 配什么 |
|---|---|---|
| 1 | 「**机器人**」页 | 每台机器人的：id、显示名、角色、**它自己的飞书应用与密钥**、所在群、发言策略、启停 |
| 2 | 「**成员**」页 | 人：成员键（`human:<名字>`）、姓名、**飞书 open_id**（没绑就认不出他在群里说话）、角色域、角色（owner/member/observer）、可批准范围 |
| 3 | 「**配置**」页 | 工作区、默认负责人、门禁超时、飞书开关、任务类型→域映射 |

配完在「配置」页点「**重新自检**」：它会真调飞书，报出凭据来源、机器人身份（名字 + open_id）、
长连接状态、机器人在哪些群、台账计数。**这一屏是排查"它为什么不说话"的第一站。**

### 3.2 配置的四个来源（顺序很重要）

```
环境变量（少量键）  >  profile 的 row config  >  <dataDir>/config.json  >  默认值
```

- **row config 压过配置文件**。所以如果 profile 的 `cordis.patch.yml` 里给某个键写了值，
  面板改它**不会生效**（保存会成功，但读出来的仍是 row 的值）。
  面板顶部会把这类键直接列出来：*"这些键被 profile 的 row config 固定住了"*。
- 配置的**真身始终是那个文件**（`~/.dsh/team/config.json`）。面板是编辑它的界面，不是它的主人：
  手写的 `//` 注释键、面板不认识的键，保存时全部原样保留。

### 3.3 四条必须知道的规矩

| 规矩 | 含义 |
|---|---|
| **保存前校验，拒绝就一个字节都不写** | 问题以 `字段路径 + 说明` 逐条返回，表单上标红 |
| **密钥只写不读** | 回显只有"已设置"+ 指纹；留空 = 不修改（空框不会把已有密钥抹掉） |
| **保存即生效** | 改了凭据或 `mode` 会就地重建长连接；**例外**是进行中任务的**门禁快照**（改超时只影响新任务） |
| **可审计** | 每次保存写一行 `config-audit.jsonl`（谁、改了哪些键、备份路径），旧文件备份成 `config.json.bak-<时间戳>`（只留最近 5 份） |

## 4. 群里怎么用

### 4.1 两种消息：一句话，或一条命令

- **一句话**（`支付这块老是超时，能不能自动重试？`）：会被分诊 → 可能变成一条**需求草稿**，
  机器人回一张需求卡。含糊的会追问一次（每个群最多 1 次，30 分钟内不重复问）。
- **一条命令**（`接受 task-1`）：直接走状态机，**不排在模型后面等**。

默认**只有被 @ 时**才回答（`feishu.requireMention: true`）。命令例外：命令随时生效。

### 4.2 命令总表（写在群里就能用）

格式：`<动词> <对象 id> [原因或人]`。第三段是可选的，`阻塞`/`转派` 这类动作需要它。

| 你输入 | 干什么 | 需要额外参数 |
|---|---|---|
| `接受 task-1` | 接受派活（门禁 1） | — |
| `开始 task-1` | 确认开始（门禁 2），此后任务才会被推动 | — |
| `提交 task-1` | 提交验收（**要附证据**，群里提交请用面板或工具） | — |
| `验收 task-1` / `通过 task-1` / `验收通过 task-1` | 验收通过 | — |
| `打回 task-1 缺单测` | 验收打回，退回执行者 | 原因可选 |
| `拒绝 task-1` | 不接这个活，回到待派发 | — |
| `转派 task-1 bot:dev` | 改派给别人（`bot:dev` 或成员名字） | **要人** |
| `交回 task-1` | 我接了但做不了，交回待派发 | — |
| `阻塞 task-1 等接口上线` | 阻塞，原因会写进任务并播报 | **要原因** |
| `解除 task-1` | 解除阻塞 | — |
| `续约 task-1` | 把租约往后推一个完整时限（"我还在做"） | — |
| `解冻 task-1` | 需求变更后被冻结的任务解冻 | — |
| `废弃 task-1 不做了` | 废弃这个任务 | 原因可选 |
| `确认需求 req-2026-001` | 确认一条需求草稿 | — |
| `确认拆解 req-2026-001` | 确认这批任务提案（也可以 `拆解 task-1`，按 id 前缀分派） | — |
| `确认变更 req-2026-001` | 需求变更已确认，重走拆解 | — |
| `完成需求 req-2026-001` | 人工标记完成（要求任务都完成） | — |
| `归档需求 req-2026-001` | 归档（转只读） | — |
| `废弃需求 req-2026-001 方向变了` | 废弃整条需求 | **要原因** |
| `挂起需求 …` / `恢复需求 …` | 挂起 / 恢复 | — |
| `状态` | 列最近 20 条任务（谁都能用，只读） | — |

> **没登记的人不能改状态**：认不出你是谁时，机器人会告诉你"先在 `feishu.senders` 里登记你的 open_id"。
> 这不是刁难，是为了让"谁确认的"这件事有据可查——否则任何人都能替别人点确认。

### 4.3 卡片怎么读

```
┌ 📋 任务 ─────────────────────── task-8891 · req-2026-014 ┐   ← 标题 + 锚点（可复制搜索）
│ 🟡 进行中 · 负责人 human:张三                              │   ← 状态行：一眼看出"什么状态、归谁"
│ ⏳ 待接受确认 · ⏳ 待开始确认 · ⏳ 待验收                   │   ← 确认行：还差谁点头
│ ──────────────────────────────────────────────────────  │
│ **验收标准** / **证据** / **⏰ 租约剩余 1d 02h** · 持有人 …  │   ← 正文
│ 操作：回复 `提交验收 task-8891` 表示「提交验收」            │   ← 按钮区（见下面的说明）
│ ⏱ 2m14s · 🧠 ≈12.3k tok · 🔄 3 步 · 🧪 CI 等待中 12m      │   ← footer：只显示"真的量到"的
└────────────────────────────────────────────────────────┘
```

三条读卡要点：

1. **`操作：回复 …`** 是**当前能做的事**。照着回复就行——卡片上的每一句，群命令都认
   （这条有测试逐字对账：词表 ↔ handler ↔ 每个状态的按钮）。
2. **footer 只显示真的上报了的字段**：provider 没报 token 就没有 🧠 那一段；**不谎报 0**。
3. **同一张卡会原地更新**，不会刷屏：同一个任务从提案到完成**只有一张卡**。
   节流窗口（2 秒）内被并掉的更新，会在几秒后补一次（否则最后一次跃迁会丢）。

### 4.4 它会自己做的事

| 行为 | 说明 |
|---|---|
| **表态** | 被 @ 的消息立刻加一个 reaction（"我看到了"），失败只记日志 |
| **回执** | 收到图片/文件会回一句"已收到图片"，并给一个 `asset://…` 引用（内容存在插件自己的盘上） |
| **追问** | 需求缺关键信息时追问一次（每群 1 次、30 分钟 TTL），**不拦着建单** |
| **去重** | 同一条消息重投（飞书会重投）只处理一次：权威键是 `event_id`，重投时 `message_id` 可能变 |
| **日报** | 每天 `feishu.dailyReportHour`（默认 18 点，本地时间）按群发一条：当天攒下的进度 + **现算的"现在有什么在等你确认"**（逐条列出还差哪道门禁、等谁） |
| **催办/升级** | 门禁到期按策略催办或升级（见 §5.3），**不会静默**：群里一定有一条消息 |
| **发言占比告警** | 某个群机器人发言占比 > 25% 且样本 ≥ 8 条时写一行 warn（按群冷却 30 分钟） |

## 5. 一条需求的完整旅程

### 5.1 状态

```
需求：draft → confirmed → dispatched → done → archived
                    ↘ changed（变更中，确认后回到 confirmed）
      任意阶段可：blocked（被外部阻塞）/ suspended（挂起）/ dropped（废弃）

任务：proposed → confirmed → assigned → accepted → in_progress → in_review → done → archived
                              ↘ rejected（拒绝，可重新指派）        ↘ blocked（阻塞，可解除）
      in_progress ⇄ ci_running（等 CI）        suspended（冻结，可解冻/废弃）
```

### 5.2 谁在什么时候点什么

| 步骤 | 谁做 | 怎么做 |
|---|---|---|
| 提需求 | 群里任何人 | 在群里 @ 机器人说一句；或 DSH 会话里调 `team` 工具 |
| 确认需求（`draft → confirmed`） | 需求负责人 | 面板按钮 / `确认需求 <id>` |
| 拆任务 | 模型或人 | `team propose_tasks` |
| 确认拆解（`→ dispatched`） | 需求负责人 | 面板 / `确认拆解 <id>`（8 小时没人确认会催办） |
| 接受（门禁 1） | 被指派的**人**本人 | `接受 <id>`；**机器人**承接时自动过（走租约） |
| 开始（门禁 2） | 同上 | `开始 <id>` |
| 执行一轮 | 任何人/模型 | 面板「▶ 执行一轮」或 `team run_task`——它会真的起一个 DSH 会话 |
| 提交验收 | 执行者 | 需要**证据**（测试结果 / diff / 产物链接 / 说明）；面板提交会写一条"人工提交，没有附证据"的备注 |
| 验收 | 各域负责人 + 需求负责人 | `验收 <id>`；**跨域任务要各方都确认**（确认会累积，缺一方不推进） |
| 收口 | 系统 | 需求下任务全部验收 → 需求自动 `done`（**这条以前是坏的，现在有专门的回归用例**） |
| 归档 | 需求负责人 | `归档需求 <id>`（转只读） |

### 5.3 门禁超时会发生什么（默认值）

| 门禁 | 默认超时 | 超时后 | 说明 |
|---|---|---|---|
| 确认拆解 | 8h | 提醒 → 升级 | 只催办，不动状态 |
| 接受 | 4h | 提醒 → 升级 | **永不自动释放**：接受代表"这活归我"，自动释放会让人莫名丢任务 |
| 开始 | 2h | **自动释放**（最多 2 次） | 放回待派发，需求负责人可重新指派 |
| 验收 | 8h | 升级给需求负责人 | 任务留在待验收 |

门禁的**超时与策略在建任务时冻结**（改配置不影响进行中的任务）；而"**谁有资格动手**"是**实时**的
（成员表改了、有人转岗，立刻生效）。

## 6. 面板六个页签

顺带记住一条：**面板的所有写操作都要填 `actor`**（顶部或页内的输入框，通常自动带出成员表第一人）。
宿主会拒绝任何没带 actor 的写操作——浏览器认证的是"浏览器"，不是"某个人"。

### 台账

- 左列「需求」：需求卡（问题 / 方案 / 验收标准 / 任务 chips / 最近历史）+ **按状态机允许的动作渲染的按钮**。
  `变更` 与 `废弃` 故意不在面板上——它们要求写原因，请用 `team` 工具（卡片会提示）。
- 右列「任务」：任务卡（门禁明细 / 租约 / 证据 / 执行会话）+ 按钮（接受 / 开始 / 提交 / 验收 / ▶ 执行一轮）。
- 顶部：「刷新」与「扫超时（预演）」——**预演只报告会做什么，不动任何对象**；结束时结果会原样显示，
  包括"还差谁确认"。

### 配置

接入自检（可点「重新自检」，会真调飞书；平时走 60 秒缓存）+ 全部可编辑配置 + 保存。
顶部会显示三类警告：被 row config 固定的键、`profile` 缺少的可选服务（如 `timer`）、配置里现存的问题。

### 机器人 / 成员 / 会话

- **机器人**：名册表（id / 显示名 / 角色 / 基准角色 / 飞书应用 / 所在群 / **配置问题** / 状态 / 操作）。
  「编辑」里改**这一台**的全部字段，**包括它自己的飞书应用与密钥**（一个机器人一个应用；没有"默认应用"）。
  配置问题逐行显示（id 冲突、两个机器人共用一个应用=同一张脸、启用了却没有密钥…），**保存前就拒绝**。
- **成员**：成员表 + 行内增删改；下面列出"没归属的发送者映射"（在群里说话但认不出是谁的 open_id）。
  角色：`owner`（可批准）/ `member` / `observer`（**只读**）。
- **会话**：上半是**群与主机器人**（群 / 主机器人 / 消息·轮次 / 上次活动 / **改主**），
  下半是每个机器人 × 每个群的会话（DSH 会话 id / 轮次 / 工作区）。

> **改主**是显式动作：它决定"这个群的消息归谁记"。回答换人不等于换主。

### 日志（出问题时第一眼看这里）

| 区块 | 回答的问题 |
|---|---|
| 分级日志（debug/info/warn/error，带计数 + 来源筛选，**连重启前的也读**） | 刚才发生了什么 |
| 收件箱（**漏单 N** + 每条消息的**原文预览**与**分诊结论**） | 有没有消息没人管？这条为什么没建单？ |
| 入站资产（`asset://` 引用 / 文件名 / 类型 / 大小） | 群里发的那张图存哪了 |
| 团队文档（条数 / 类型分布 / **过期的那几行与原因**） | 哪份文档该更新了 |
| 投递统计（**降级率**：落盘口径 + 本进程口径、逐级条数、@人次数） | 卡片是不是渲染不出去了 |
| 每群机器人发言占比（> 25% 标红，样本不足会说明原因） | 机器人是不是太吵了 |

三个口径提醒：**降级率**用落盘口径（一行台账 = 群里一条消息，跨重启成立）；
「本进程」那个是逐次投递、重启清零；**漏单**只数"看了、什么都没产出、也没写原因"的消息。

## 7. 数据放在哪（备份就是备份这个目录）

```
~/.dsh/team/                       ← dataDir（env DSH_TEAM_DATA 可改）
├── config.json                    真身；.bak-<时间戳> 最近 5 份
├── config-audit.jsonl             每次保存一行（谁、改了哪些键）
├── requirements/ tasks/ leases/ decisions/ runs/ chats/ bot-sessions/ cards/
│                                  一对象一个 JSON 文件，可以直接 cat / 手改
├── inbox/messages.jsonl           入站消息（append-only，最后一行赢）
├── logs/team.jsonl                结构化日志（2MB 轮转一份；写入前脱敏）
├── assets/<id>/<原名>             入站图片/文件 + index.jsonl
├── load-report.txt                插件加载/激活失败的一行记录
└── workspace/                     执行会话的 cwd，也是团队文档库的根
    ├── docs/                      specs/ decisions/ runbooks/ meetings/ notes/ …
    └── _meta/docs.json            文档索引（机器读的那份，可重建）
```

- **备份**：备份 `~/.dsh/team` 就等于备份了台账、收件箱、日志、资产与配置。
- **保留窗口**：入站消息按 `feishu.dedupeRetentionDays`（默认 30 天）每小时清一次；
  日志 2MB 轮转。**资产不自动删**（它是消息内容，不是过程数据）。
- **重启语义**：`lib/team.js` 及其依赖是动态加载（按文件 mtime），保存后重新激活即可；
  **入口 `lib/index.js` 与 `cordis.patch.yml` 的改动要重启宿主**。

## 8. 文档与记忆

**沉淀知识写工作区文件**（`workspace/docs/`），**情景记忆查 DSH 会话历史**——不另建记忆库。

```console
# 建文档库（按规范建目录 + 第一份 index.md）
team docs op=init
# 写一份文档：**frontmatter 是硬要求**（缺 owner 之类的必填字段一个字节都不写）
team docs op=write id=adr-2026-009 type=decision title=记忆不建库 owner=human:pm body="…"
# 沉淀一条结论（默认落 draft，等人确认后改 active）
team remember title="发布流程要先跑单测" body="约定：合并前必须绿" owner=human:pm
# 重建索引（index.md 与 _meta/docs.json 都是**派生物**，手改会被覆盖）
team docs op=index
# 谁过期了
team docs op=stale
# 回忆：一次查文档 + DSH 会话历史 + 台账
team recall query=退避
```

两条约定：**过期的文档照样能搜到**，但会标出来（"不知道"比"知道过期的"更糟）；
查不到的那一半会**如实说没查**（比如这个 profile 没有 `sessionQuery`），而不是拿空数组糊弄。

## 9. 代码仓库与 CI

**先说做不到的**：卡片按钮与 Git webhook 都要公网入站 HTTPS，而 DSH Web 只监听 `127.0.0.1`。
所以真正检出 / 提交 / 开 MR / 合并的是**执行会话里的 `git` / `gh`**；插件负责约定、判定、记录：

| 事 | 怎么做 |
|---|---|
| **分支与提交约定** | 需求分支 `req/<需求>-<slug>`，任务分支 `req/<需求>/<任务>`；**每条提交**带 `Req: …` / `Task: …` trailer。代码类任务的 prompt 里会直接写上这三条 |
| **记 MR** | `team repo op=link_mr id=task-1 url=<MR 链接> files=[…]`（`files` 里若有接口契约/迁移/配置模板，相关文档会自动标 stale） |
| **能不能合并** | `team repo op=merge`：三道门一起判——**至少一个人类审批** + **CI 通过** + **执行者够格**（只有 ops 或明确可批准的人能合并）。被挡时逐条返回 blocker |
| **CI 状态机** | `team ci op=start/pass/fail`；超时（默认 30 分钟）会在群里播报一次"CI 迟迟没有结论"，卡片 footer 显示 `🧪 CI 等待中 12m` |
| **仓库知识索引** | 配好 `repos.roots`（仓库名 → 本地检出路径）后 `team repo op=overview repo=<名字>`，生成 `docs/specs/<repo>-overview.md`——机器人改代码前先读它 |

## 10. 权限速查

三层闸各管各的（都真的拦人，不是提示词）：

| 层 | 判什么 | 在哪配 |
|---|---|---|
| **领域层** | "这个主体配不配做这个动作"（跨域要各方确认、执行者不能自己验收、出题者不能当阅卷人…） | 状态机，不可配 |
| **组织层** | "这个人现在能不能动手"：`observer` 只读、停用的人要走代理、`canApprove` 是白名单 | 「成员」页 |
| **机器人层** | "这台机器人有没有这个能力 / 能不能碰这个仓库" | 「机器人」页的 `capabilities` / `scope` |

机器人角色的默认能力（`cannot` 是默认禁止的）：

| 角色 | 默认不能 |
|---|---|
| `req` 需求 | ✍️ 写代码、合并、部署 |
| `dev` 开发 | 合并、部署 |
| `qa` 测试 | 合并、部署 |
| `coord` 调度 | 写代码、合并、改需求原文 |
| `lib` 资料 | 合并、部署 |
| `ops` 运维 | ——（部署需要批准） |

**群准入**三道：`feishu.requireRegisteredChat`（每个群都要有归属）、`feishu.chatAllowlist`
（写了一张白名单就打开准入；它与机器人自己的 `chats` 取**并集**）、`bots[].feishu.chats`（谁回答）。

**成员表的白名单规则**：名册**空的**时候不限制（还没建名册的安装不该谁都动不了）；
名册**非空**时它就是白名单——不在表里的 `human:` 写不动。`bot:`/`role:`/`system` 归机器人那层管。

## 11. 常用配置项

| 键 | 默认 | 作用 |
|---|---|---|
| `workspace` | `<dataDir>/workspace` | 执行会话的工作目录 + 文档库根 |
| `defaultOwner` | `human:owner` | 建需求没写 owner 时的兜底（**名册非空时，它必须在名册里**，否则建单会被拒） |
| `tickIntervalMs` | `60000` | 门禁/租约扫描周期；`0` = 关掉（改成手动 `tick`） |
| `gates.*` | 见 §5.3 | 四道门禁的超时与策略（只影响新任务） |
| `members` | 每人一行 | 成员表（角色域分配在人身上） |
| `feishu.mode` | `own` | `own` = 自己拨号；`off` = 不收消息（出站卡片仍可用） |
| `feishu.requireMention` | `true` | 群里只有被 @ 才回答（命令不受限） |
| `feishu.respond` | `true` | 关掉 = 只记录/建单，不回答 |
| `feishu.buttons` | `false` | **本版本必须保持 false**（没有回调端点，打开会得到死按钮；配置台会拒绝） |
| `feishu.speakLeaseMs` | `90000` | 两个机器人都可能接话时，先说话的把群占住多久 |
| `feishu.dedupeRetentionDays` | `30` | 去重表的保留窗口（也决定日志页能回看多久）；`0` = 不清理 |
| `feishu.dailyReportHour` | `18` | 日报时刻（**本地时间**）；`-1` = 关 |
| `feishu.reaction` | `true` | 被 @ 时先表态 |
| `feishu.ask.maxAsks` / `ttlMs` | `1` / 30 分钟 | 追问次数与过期 |
| `repos.roots` | `{}` | 仓库名 → 本地检出路径（仓库索引要扫真实目录） |
| `repos.ciTimeoutMs` / `requiredApprovals` / `autoMerge` | 30 分钟 / 1 / `false` | `ci_stuck` 判定线、合并前至少几个审批、自动合并 |

完整清单（56 个键）见 `config.example.json`；面板可编辑 26 项。

## 12. 排障手册

| 症状 | 先看这里 | 常见原因 |
|---|---|---|
| 侧栏没有「团队台账」 | `~/.dsh/team/load-report.txt`、`logs/team.jsonl` 的 `boot` 行 | 起的是 headless；没带 `?token=`；插件加载失败（原因就写在那两个文件里） |
| 面板打开一直转 / 读取超时 | 「配置」页的接入自检 | 路由没挂（同"侧栏没有入口"三条）；飞书接口慢（自检已加 60 秒缓存） |
| 面板写着**「宿主半边没能起来（activate）：……」** | 那句话本身就是原因；完整堆栈在 `load-report.txt` | 插件宿主那一半激活时抛错了（面板是静态脚本，所以照常显示、页签都在，接口却一个都不在）。**重启宿主**通常就够；还不行就把那一行连同堆栈贴给维护者 |
| 面板写着「读取失败：HTTP 404 的响应不是 JSON」 | 同一行的后半句 | 一是插件行没挂载（看 `load-report.txt` / `logs/team.jsonl` 的 `boot` 行）；二是这个 profile 没有 `connection` 服务。**宿主半边激活失败时面板会直接把原因写在页面上**，看不到那句话就说明是这两条之一 |
| 群里 @ 它没反应 | 「日志」页收件箱：这条消息在不在？**分诊结论**是什么 | 没绑定 open_id（认不出你是谁）；群不在准入范围；机器人没启用 / 没密钥；`speakPolicy` 不允许它开口 |
| 群里一句话没变成需求 | 收件箱里那条的**分诊结论** | 判成 status/question/smalltalk（词表与上下文窗口决定）；重复并入已有需求 |
| **漏单 > 0** | 收件箱里没有 `ignored_reason` 的那几条 | 看了没产出也没写原因——多半是分诊/提取模块没加载，或建单被拒（原因就在那一行） |
| 卡片按钮点不动 | —— | **本版本没有回调端点**，按钮是死的；请照卡上的文本指令回复（配置台会拒绝把 `buttons` 打开） |
| 任务卡住了 | 「台账」页任务卡的门禁明细 | 门禁还差谁确认；任务 `assigned` 且没人接受（`接受` 命令）；`suspended`（需求变更后要 `解冻`）；`blocked`（要 `解除`） |
| 群里没动静但任务动了 | 「日志」页投递统计 | 被节流/聚合/静默（都是"决定了不说"，不是丢消息）；没有来源群（DSH 里建的需求不回群） |
| 保存配置没生效 | 面板顶部的"被 row config 固定的键" | 那些键来自 profile 的 `cordis.patch.yml`，优先级高于配置文件 |
| 门禁超时、日报、补发全都不发生 | 面板顶部的"缺少可选服务" | 这个 profile 没有 `timer`；可用「扫超时」手动兜底（`tick` 的 `dry_run: false` 才真的动状态） |
| 需求永远不完成 | 台账页需求卡 + 任务状态 | 有任务没验收（`dropped` 的会被忽略，其余都要 `done/archived`） |
| 两个机器人抢话 / 同一个群两张卡 | 「会话」页的群与主机器人 | 一个群只该有一个主；`speakLeaseMs` 管发言租约；同一话题的卡会原地更新 |

## 13. 做不到的事（诚实清单）

| 做不到 | 为什么 | 现在怎么办 |
|---|---|---|
| 卡片按钮真的能用 | 按钮要公网 HTTPS 回调，DSH Web 只监听 `127.0.0.1`；插件也不注册 `card.action.trigger` | 确认动作走**群文本命令**；卡片会写明回复哪一句 |
| Git 平台 webhook / 一键合并 | 同上 | agent 在工作目录里用 `git`/`gh` 自己开 MR；插件记关联、判合并、播报 CI |
| 语音 / 转发合并 / 撤回 / 表情回应当信号 | 这四类入站事件还没接（当前会落库但不建单） | 语音请补一句文字；转发内容请贴文本 |
| 审批三档（允许一次 / 本次会话 / 始终） | 要接 DSH 的 approval 服务，尚未做 | 高风险动作靠 `canApprove` 白名单 + CI 判定 |
| 任务有"计划步数/进度百分比" | 没有计划层；footer 的 `🔄 N 步` 是**上一轮的工具调用数** | 用 `blocked_reason`、证据与日报表达进展 |
| token/成本按天按机器人聚合 | 只做了"每轮上报/不谎报"，没做记账聚合 | 卡片 footer 有单轮 token；`budget` 字段已可用但未强制 |
| 飞书文档镜像（工作区 → 云文档） | 需要文档 API 与配额管理，未做 | 工作区是主副本；需要移动阅读时人工导出 |
