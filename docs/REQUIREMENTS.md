## 0. 一句话需求

**把飞书群里的协作变成有状态、可查询、可追溯的对象，并让任务真的被 DSH 会话执行掉 ——
以"一个 DSH 插件行"的形态，不新建任何服务。**

三个已定前提（与旧需求最大的区别就在这里）：

1. **载体是 DSH 插件行**（Cordis row，进程内），不是自建平台；
2. **需求卡/任务卡是系统对象**，飞书与面板都只是视图；
3. **沟通不等于需求** —— 群里绝大多数消息是沟通，只有"有实质内容且表达诉求"的才成为对象。

## 1. 不可协商的前提（形态约束）

这些不是取舍，是**边界**。任何需求条目与它们冲突时，条目作废（改写或删掉）。

| # | 约束 | 它排除掉了什么 |
|---|---|---|
| C1 | **一个插件行**：进程内，没有自己的服务、端口、数据库、队列中间件 | 自建 Hub / 常驻守护进程 / 自研 Web 控制台 / SQLite / MQ |
| C2 | **通信面是飞书长连接，我们自己拨号，没有公网入站** | 卡片按钮与回调、Git 平台 webhook、任何"点一下就触发服务端"的交互 |
| C3 | **一个飞书应用 = 一条长连接 = 一个身份** | "同一个应用里给每个机器人一个身份"；要多个身份就配多个应用 |
| C4 | **配置的真身是一个文件**（`$DSH_HOME/team/config.json`，人可 `vim`），面板是编辑它的界面，不是它的主人 | 把配置存进数据库、面板独有的配置、手写注释被面板吃掉 |
| C5 | **单一写入者**：团队对象只由持插件的那个进程写 | 多人/多机同时写同一份台账、对等同步 |
| C6 | **模型与预算归 DSH**：插件不实现路由、降级链、预算 | 插件内的 `models.routing` / 成本闸门（成本闸门是分诊层） |
| C7 | **浏览器半边零构建**（手写经典脚本 + 平台注入的 React）：配置坏掉时面板也得能打开 | 面板依赖构建产物、依赖它自己要救的那套配置 |
| C8 | **可选服务缺失只降级、不阻断**（`agents`/`timer`/`connection`/`sessionQuery`/`tokenMeter`/`workspaceRegistry`） | "没有 X 就整个插件不工作"；声明可选服务会把整行停住 |
| C9 | **入站判重与副作用顺序**：判重必须在下载、落库、回执、建单**之前** | "先处理再判重"（会产生重复对象与重复副作用） |

## 2. 用户与场景

| 角色 | 在哪 | 要什么 |
|---|---|---|
| **团队负责人** | 群里 + 面板 | 派活不靠喊；看得见谁卡在哪；改配置不用改代码；出事能查 |
| **团队成员** | 群里 + 面板 | 被派活时能接受/拒绝；状态变了不用问；不用学新工具 |
| **机器人** | 群里（一个角色一个身份） | 能建单、能拆解、能承接、能真跑一轮并交证据；不刷屏 |

## 5. 整体验收标准（MVP 是否成立）

跑得通**这一条链**才算成立：
**群里一句话 → 分诊 → 建需求 → 确认拆解 → 任务两道确认 → 真起执行会话跑一轮 → 证据回写 → 群里播报 → 验收 → 需求完成。**

| # | 验收项 | 判据 | 现状 |
|---|---|---|---|
| 1 | 不丢需求 | 触发消息要么有对象、要么有明确"不是需求"的原因 | ✅（每条都有结论；漏单率的分母未算） |
| 2 | 卡片可原地流转 | 一个任务全程一张卡 | ✅ |
| 3 | 两道确认真的拦住 | 未接受不 `in_progress`；未开始不执行 | ✅ |
| 4 | 超时有去处 | 催办/升级/自动释放都出声 | ✅（但没有 `notify_window`） |
| 5 | 完成有证据 | `done` 的任务卡有证据 | ✅ |
| 6 | 没人被绕过 | 未登记的人写入被拒；未登记群不处理 | 🟡（群准入默认关且位置偏晚） |
| 7 | 重启不重复 | 重投事件不产生第二条任务/第二张卡 | ✅ |
| 8 | 机器人不刷屏 | 群内机器人消息占比 < 25% | ✅ 指标在；**"试运行一周"未做** |
| 9 | 端到端实测 | 真 harness + 真模型 + 真飞书协议层跑过一次完整闭环 | ✅（`README.md` 的"实测"节：`req-2026-001` → `task-1` → 执行会话读到文件 → 证据回写 → `in_review`） |
