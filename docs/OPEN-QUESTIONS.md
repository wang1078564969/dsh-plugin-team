## 1. 什么算一条需求？（2026-09-12 挂起）

**问题**：现在"被 @ 了就算需求"。`@机器人 我的角色是什么` 这样的问句，群里就多一张
**待澄清** 的需求卡（`req-2026-005`）。使用者的原话：

> 现在这样控制有点太严苛了，限制了跟机器人沟通。

**今天在跑的两条判据**（跑的是真代码 + 真配置，`lib/feishu/triage.js` + `lib/feishu/ingest.js:621`）：

| 群里说的话 | 分诊 | `addressedOverridesIntent: true`（出厂默认） | `false`（本部署现在） |
|---|---|---|---|
| 我的角色是什么 | status | 建卡 | **不建卡** |
| 为什么构建失败了 | question | 建卡 | **不建卡** |
| 帮我加个重试 | requirement | 建卡 | 建卡 |
| 导出按钮点了没反应，修一下 | requirement | 建卡 | 建卡 |
| 导出按钮点了没反应 | status | 建卡 | **不建卡** ← 代价在这 |
| 支付重试已经上线了 | status | 建卡 | **不建卡** |

**临时决定（本部署）**：`~/.dsh/team/config.json` 里 `feishu.addressedOverridesIntent = false`
（面板「配置」页同一个开关）。@ 也要命中诉求词才建卡；问句、闲聊、进度同步只回答，不建卡。
**出厂默认值没动**（仍是 `true`）—— 判据本身还没想清楚，不该顺手改所有人的行为。

**要回答的问题**：

1. 判据用**词表**（现在这样）、**模型分类**（每个群本来就有会话和 LLM 在后面），还是
   **人显式立需求**（`@机器人 需求：…` / 一个 `建需求` 动词）？三者的失败方向不同：
   词表漏真诉求、模型会漂、显式最准但要人多打几个字。
2. 「漏掉一条真诉求」和「多一张噪声卡」哪个代价大？现在选的是**宁多勿漏**，代价由人承担
   （手动 `废弃需求`）—— 使用者已经明确说这个代价他不想要，但换成宁漏勿多，
   第一次漏掉 bug 报告时的感觉可能更差。
3. 草稿卡要不要**发到群里**？还是只进面板、群里只回一句"我记下了"？
   群消息是稀缺资源，一张卡占掉半屏。
4. 问句识别太窄：`question_patterns` 只有 `[?？]$` 与
   `^(怎么|如何|为什么|为啥|什么时候|谁|哪个|是否)`，所以「我的角色是什么」落进 `status`。
   若要走"问句不建卡"，中文问句模式得重新想 —— 而且**不能**把
   「能不能加个重试」（这是需求）误判成问句：它的诉求词优先级更高，顺序不能反。
5. `draft` 的归宿：靠人废弃（现在），还是**超时自动过期**（例如 24 小时无人确认就归档）？
   自动过期要防的是"认真提的需求被静默丢掉"，所以过期前必须已经在群里说过一次。

**改动落点**（动手前先读）：`lib/feishu/triage.js`（七步判据）、`lib/feishu/ingest.js:621`
（@ 放宽那一段，注释里写着这个取舍的来由）、`lib/feishu/extract.js:179`（`directAddress` 分支）、
`lib/settings.js`（面板能不能改）、`docs/DESIGN.md` §6 第 8 步。测试：`test/triage.test.mjs`、
`test/inbound.test.mjs`（`addressedOverridesIntent: false` 那条用例已经在跑）。

## 2. 身份映射能不能自己长出来？（2026-09-12 挂起）

**问题**：群命令要认人（`feishu.senders`: open_id → `human:<名字>`），而这张表是**手填**的。
没填时：卡片上写着"回复 `确认需求 req-2026-005`"，而这句话会被拒绝 ——

```
✖ 认不出你是谁：这台人的飞书 open_id 还没有映射到成员，先在团队配置的 feishu.senders 里登记（ou_…）
```

也就是说**卡片教人做一个当前做不到的动作**。而且 open_id **按应用隔离**：同一个人，
应用 A 看到 `ou_c5d0…`、应用 B 看到 `ou_44e7…`（实测，两个应用各查了一次同一个群的成员），
所以一个人有几个应用就要填几行 —— 让人手填这件事本身是错的形状。

**已有的线索**：应用有 `im:chat` 读权限时，`GET /open-apis/im/v1/chats/<chat_id>/members?member_id_type=open_id`
就能拿到成员的名字与（该应用命名空间下的）open_id。实测两个应用都读得到。

**候选路线**：收到消息时按 open_id 在群成员表里查出名字 → **面板提示"发现群成员 王梦凡，
绑到 human:wangmengfan？"**，人点一下确认（不自动绑：名字到主体该由人认一次，自动绑等于猜）。
配套问题：名册里现在只有 `human:wangmengfan` 这样的 key，没有中文名 —— 要么给人加 `name` 字段，
要么绑定时让人从名册里挑。

**为什么不做自动绑**：认错人比认不出人更糟 —— 认错会让"只有负责人能确认"这道闸形同虚设。
